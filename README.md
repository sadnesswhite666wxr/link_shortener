# 🔗 LinkStat

[![Статус Workflow](https://github.com/sadnesswhite666wxr/link_shortener/actions/workflows/ci.yml/badge.svg)](https://github.com/sadnesswhite666wxr/link_shortener/actions)

Высоконагруженный асинхронный микросервис сокращения ссылок, спроектированный по канонам **Чистой Архитектуры (Clean Architecture)**. Оптимизирован под Highload-нагрузки, защищен от рассинхронизации данных при параллельных запросах и снабжен enterprise-инфраструктурой обсервабилити.

---

## 🏗 Архитектурные особенности и infrastructure-решения

*   **Интеграция кэширования (Паттерн Cache-Aside):** Для снижения нагрузки на реляционную СУБД реализован слой кэширования в Redis. Чтение данных (информации о ссылках и профилей пользователей) оптимизировано через быстрый кэш в оперативной памяти. При операциях обновления или удаления (`update`/`delete`) старые данные инвалидируются в Redis строго после выполнения коммита.
*   **Конкурентная обработка запросов:** Настройки асинхронного пула соединений SQLAlchemy (`pool_size=50`, `max_overflow=100`) сбалансированы под параллельную обработку входящих сетевых пакетов, страхуя базу данных от нехватки сокетов при пиковых нагрузках.
*   **Безопасность аутентификации:** Реализована базовая защита от атак по времени (Timing Attacks) на эндпоинте авторизации. Это выравнивает время ответа сервера и не позволяет злоумышленникам перебором определять существующие в системе логины.
*   **Ролевая модель доступа (RBAC & Object-Level):** Разграничение прав реализовано по схеме RBAC (Пользователи — Роли — Права) с интеграцией на уровне зависимостей FastAPI через механизмы `Depends` и `SecurityScopes`. Дополнительно на уровне бизнес-логики сервисов внедрена проверка владения конкретным ресурсом (Object-Level проверки), разделяющая доступ к собственным записям (`READ_OWN`) и сквозные административные действия (`READ_ALL`).
*   **Контейнеризация и изоляция:** Проект упакован в легковесный и защищенный образ на базе Alpine Linux. Процесс приложения изолирован от прав суперпользователя и выполняется от некорневого `USER guest`. Доступы к PostgreSQL и Redis ограничены внутри приватной сети Docker с помощью директивы `expose`.

## 🛠 Технологический стек & Инструменты

- **Core:** Python 3.12, FastAPI, SQLModel, Pydantic v2
- **Data & Caching:** PostgreSQL 18, Redis 7
- **Crypto & Auth:** OAuth2 (Bearer), PyJWT, pwdlib
- **Observability:** Prometheus, Grafana, Structlog
- **DevOps & CI/CD:** Docker, Docker Compose, Poetry 2.0+, GitHub Actions

## 📦 Быстрый старт и развертывание

### 1. Подготовка окружения
Клонируйте репозиторий и создайте локальный файл `.env` на основе готового шаблона `.env.example`:

```bash
cp .env.example .env
```

### 2. Запуск стека в Docker
Локальный запуск всей экосистемы (включая автоматический накат миграций Alembic и запуск сидирования базы данных дефолтными пользователями) выполняется одной командой:
```bash
docker compose up --build -d
```

### 🏁 Доступные интерфейсы:
* **API Swagger UI:** `http://localhost:6060/docs`
* **Healthcheck:** `http://localhost:6060/system/health`
* **Метрики Prometheus:** `http://localhost:6060/system/metrics`
* **Мониторинг:** Grafana (`http://localhost:3000`) & Prometheus UI (`http://localhost:9090`)

## 🚀 Автоматизация CI/CD

В репозиторий интегрирован непрерывный контроль качества кода через **GitHub Actions**. При обновлении веток автоматически запускаются следующие этапы:
1. **Форматирование:** Проверка стандартов отступов силами `black --check`.
2. **Линтинг:** Анализ кода с помощью `ruff check` для поиска неиспользуемых импортов и синтаксических ошибок.
3. **Сборка в Docker:** Тестовая сборка production-образа `Dockerfile` для проверки корректности компиляции контейнера.
